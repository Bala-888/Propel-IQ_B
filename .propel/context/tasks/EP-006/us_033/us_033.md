# User Story - US_033

## Story ID
* ID Format: US_033

## Story Title
* Real-time queue push to all connected staff clients via SignalR

## Description
* As a **staff member**, I want the queue dashboard to update automatically when new patients are added or their status changes, so that I always have current information without manually refreshing the page.

## Acceptance Criteria

### AC-001: New queue entry is pushed to all connected staff clients within 2 seconds
- **Given**: At least one staff client is subscribed to the SignalR hub `/hubs/queue`
- **When**: A new booking or walk-in creates a queue entry
- **Then**: The `QueueEntryAdded` event is broadcast to all connected staff clients within 2 seconds, the new row appears in SCR-011 with a highlight animation (UXR-502), and the summary count increments — without the staff member refreshing the page

### AC-002: Status change events are pushed to all connected clients within 2 seconds
- **Given**: A staff member marks a patient as arrived (us_032)
- **When**: The PATCH call commits
- **Then**: A `QueueEntryUpdated` event is broadcast via SignalR and all other open SCR-011 instances reflect the status change within 2 seconds — no stale "Waiting" status remains on other clients

### AC-003: New row appears with a highlight animation then fades
- **Given**: A `QueueEntryAdded` event arrives at a client
- **When**: The new row renders in the queue table
- **Then**: The row background uses a `--color-highlight` CSS variable initially, then transitions to the default row colour via a 1.5-second CSS fade transition — meets UXR-502

### AC-004: Reconnection recovers missing events
- **Given**: A staff client disconnects for up to 30 seconds due to a network interruption
- **When**: The SignalR client reconnects
- **Then**: All queue events missed during the disconnection are replayed via a `GET /queue?since=<lastEventTimestamp>` fallback call, and the table state is reconciled without duplicates

### AC-005: SignalR hub enforces Staff/Admin role authorisation
- **Given**: An unauthenticated or Patient-role user attempts to connect to `/hubs/queue`
- **When**: The connection handshake is evaluated
- **Then**: The server rejects the connection with HTTP 401 (unauthenticated) or HTTP 403 (wrong role) — no queue events are exposed to non-staff users

## Edge Cases
* **Hub has 0 connected clients**: A queue entry creation when no clients are connected must not throw an unhandled exception — the broadcast call must be fire-and-forget with no impact on booking commit.
* **Broadcast lag > 2 seconds under load**: If 50 staff clients are connected simultaneously and broadcast latency exceeds the 2-second SLA, the system must still commit the underlying data mutation — the SLA breach must be logged to Seq as a warning but must not cause a transaction rollback.
