# User Story - US_041

## Story ID
* ID Format: US_041

## Story Title
* AI conflict detection job identifies clinical entity conflicts and surfaces them to staff

## Description
* As a **clinician or staff member**, I want the system to automatically detect clinical conflicts (e.g., drug interactions, duplicate diagnoses) in a patient's extracted entities and surface them for review, so that safety issues are flagged before the patient's visit.

## Acceptance Criteria

### AC-001: Conflict detection job runs when a patient's entity set is updated
- **Given**: A `PatientEntitiesUpdated` domain event is raised after us_038 completes extraction
- **When**: The `ConflictDetectionService` handles the event
- **Then**: The service retrieves all `patient_entities` for the patient and invokes the Ollama conflict analysis prompt to identify entity conflicts — the analysis completes within 30 seconds for a patient with up to 200 entities

### AC-002: Detected conflicts are stored in the `clinical_conflicts` table
- **Given**: The Ollama analysis identifies a drug interaction between two medications in the patient's entity list
- **When**: The conflict response is parsed and validated
- **Then**: A row is inserted in `clinical_conflicts` with `patient_id`, `entity_a_id`, `entity_b_id`, `conflict_type` (e.g., `"DrugInteraction"`), `description`, `severity` (`"Low" | "Medium" | "High"`), and `status = "Open"`

### AC-003: Open conflicts are displayed on SCR-014 in the Conflicts panel
- **Given**: A patient has at least one `status = "Open"` conflict in `clinical_conflicts`
- **When**: `GET /patients/{id}/summary` is called
- **Then**: The `conflicts` array in the response includes all open conflicts with `entity_a`, `entity_b`, `conflict_type`, `description`, and `severity` — rendered in SCR-014 with severity badge (text + icon per UXR-105)

### AC-004: Conflict detection is idempotent — re-analysis does not create duplicate conflict rows
- **Given**: The conflict detection job runs twice for the same patient with the same entity set
- **When**: The second run attempts to insert conflicts
- **Then**: `INSERT ... ON CONFLICT DO NOTHING` (or equivalent upsert) ensures no duplicate rows in `clinical_conflicts` — `SELECT COUNT(*) FROM clinical_conflicts WHERE patient_id = <id> AND entity_a_id = <x> AND entity_b_id = <y>` returns 1

## Edge Cases
* **Ollama returns unparseable conflict output**: If the Ollama conflict analysis response is not valid JSON or does not match the expected schema, the conflict detection service must log `eventType = "ConflictDetectionSchemaError"` and exit without persisting any conflicts — the patient record must not be corrupted with partial data.
* **Patient has only one entity**: Conflict detection requires at least two entities to compare. If `patient_entities` returns fewer than 2 rows, the job must exit early without calling Ollama — logging `eventType = "ConflictDetectionSkipped"` with `reason = "InsufficientEntities"`.
