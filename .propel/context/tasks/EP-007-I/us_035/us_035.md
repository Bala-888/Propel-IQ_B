# User Story - US_035

## Story ID
* ID Format: US_035

## Story Title
* Patient document upload with MIME type validation and AES-256 encrypted storage

## Description
* As a **patient**, I want to upload medical documents securely, so that my files are stored encrypted and only accepted when they meet the required format constraints.

## Acceptance Criteria

### AC-001: Upload form accepts only PDF and DOCX MIME types
- **Given**: A patient is on SCR-009 (Document Upload) and attempts to upload a PNG image
- **When**: The file is selected and submitted
- **Then**: The API returns HTTP 400 with `{"error": "Unsupported file type. Only PDF and DOCX are accepted."}` and no file data is written to storage — validated server-side by inspecting the MIME type signature, not the file extension alone

### AC-002: File size is rejected above 25 MB
- **Given**: A patient attempts to upload a 30 MB PDF
- **When**: `POST /documents/upload` receives the file
- **Then**: The API returns HTTP 413 with `{"error": "File exceeds the 25 MB size limit."}` before any file bytes are persisted

### AC-003: Accepted file is encrypted with AES-256 before being stored
- **Given**: A valid PDF within the size limit is uploaded
- **When**: The upload pipeline processes the file
- **Then**: The file bytes are encrypted using AES-256-GCM with a per-document key derived from the platform key store, the cipher text is persisted to the configured blob storage, and the unencrypted bytes are never written to disk

### AC-004: Document metadata record is created in the database on successful upload
- **Given**: The encrypted file is persisted
- **When**: The upload pipeline completes
- **Then**: A `document_records` row is inserted with `patient_id`, `original_filename`, `mime_type`, `size_bytes`, `upload_timestamp`, `status = "Uploaded"`, and the `blob_path` of the encrypted file — HTTP 201 is returned to the client with `{"documentId": "<uuid>", "status": "Uploaded"}`

### AC-005: Mobile file input has a fallback for direct camera capture
- **Given**: A patient is accessing SCR-009 on a mobile device
- **When**: The file input renders
- **Then**: The `<input type="file" accept=".pdf,.docx" capture="environment">` attribute is set, enabling direct capture from the device camera as a fallback upload method — meets UXR-303

## Edge Cases
* **Concurrent uploads of two documents by the same patient**: Each upload must produce an independent `document_records` row with a unique `documentId` — no race condition between concurrent uploads must overwrite either record.
* **Upload interrupted mid-stream**: If the connection is dropped mid-upload, the partially written file must be cleaned up by the storage layer (atomic write or temp-file swap), and the `document_records` row must not be created — the patient must be able to retry without orphaned storage objects.
