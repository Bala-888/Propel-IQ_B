# User Story - US_039

## Story ID
* ID Format: US_039

## Story Title
* Document processing status machine with 120-second pipeline timeout and retry CTA

## Description
* As a **patient**, I want to see a live processing status for my uploaded document, so that I know when it is ready or if there was a problem and I can retry without contacting support.

## Acceptance Criteria

### AC-001: SCR-010 displays the current document status in real time
- **Given**: A patient has uploaded a document and is on SCR-010 (Document Processing Status)
- **When**: The page loads and polls `GET /documents/{id}/status` every 5 seconds
- **Then**: The displayed status reflects the current `document_records.status` value: one of `Uploaded → TextExtracted → Chunked → EmbeddingsComplete → EntitiesExtracted`, with a progress stepper component showing the completed and pending stages

### AC-002: A document that has not reached "EntitiesExtracted" within 120 seconds is marked TimedOut
- **Given**: A document enters the processing pipeline and `processing_started_at` is set
- **When**: 120 seconds elapse and `status != "EntitiesExtracted"`
- **Then**: The pipeline guardian sets `document_records.status = "TimedOut"`, logs `eventType = "DocumentProcessingTimeout"` to Seq with `level = "Error"`, and no further processing steps are attempted for that document

### AC-003: TimedOut status shows a Retry CTA on SCR-010
- **Given**: `GET /documents/{id}/status` returns `{"status": "TimedOut"}`
- **When**: SCR-010 renders the status
- **Then**: The status stepper shows `"Processing timed out"` at the current step, an error icon + text message (not color alone — UXR-603) reads "Document processing failed. Please try again.", and a "Retry" button is visible that calls `POST /documents/{id}/retry` — meets UXR-603

### AC-004: Retry resets the document to "Uploaded" and restarts the pipeline
- **Given**: A patient clicks "Retry" on SCR-010 for a TimedOut document
- **When**: `POST /documents/{id}/retry` is called
- **Then**: `document_records.status` is reset to `"Uploaded"`, `processing_started_at` is reset to the current timestamp, the pipeline is re-triggered from the beginning, and the status stepper on SCR-010 resets to the first step

### AC-005: ExtractionFailed status also shows the Retry CTA
- **Given**: `document_records.status = "ExtractionFailed"` (from us_036)
- **When**: SCR-010 renders
- **Then**: The same Retry CTA as AC-003 is displayed — the Retry CTA must be shown for both `TimedOut` and `ExtractionFailed` states

## Edge Cases
* **Concurrent retry calls for the same document**: `POST /documents/{id}/retry` must be idempotent — if two retry calls arrive simultaneously, only one pipeline restart must be queued. The second call must return HTTP 200 without creating a duplicate processing job.
* **Document in terminal "EntitiesExtracted" state receives a retry call**: If `POST /documents/{id}/retry` is called on an already-complete document, the API must return HTTP 409 with `{"error": "Document processing is already complete."}` — the pipeline must not be re-triggered.
