# User Story - US_015

## Story ID
* ID Format: US_015

## Story Title
* AES-256 PHI encryption at rest and TLS 1.2+ enforcement in transit

## Description
* As a **HIPAA compliance officer**, I want all PHI encrypted with AES-256 before database persistence and all data in transit protected by TLS 1.2 or higher, so that a storage breach or network intercept cannot expose readable patient health information.

## Acceptance Criteria

### AC-001: Direct database dump contains no plaintext PHI
- **Given**: A patient record with known `email`, `phone`, and `dateOfBirth` values has been saved via the API
- **When**: `pg_dump` is used to extract the `patients` table and the output is searched for the plaintext `email` value using `grep`
- **Then**: `grep` returns no matches — the PHI columns contain only pgcrypto ciphertext

### AC-002: TLS 1.0 and 1.1 connections are rejected at Nginx
- **Given**: Nginx is configured with `ssl_protocols TLSv1.2 TLSv1.3` (no earlier versions)
- **When**: `openssl s_client -connect localhost:443 -tls1_1` is executed
- **Then**: The connection is refused with `SSL routines::no protocols available` — no data exchange occurs

### AC-003: API-to-database traffic does not traverse unencrypted channels
- **Given**: The .NET API is configured with a PostgreSQL connection string using `Ssl Mode=Require`
- **When**: A network packet capture is taken on the Docker bridge between the `api` and `db` containers
- **Then**: The PostgreSQL wire protocol data is encrypted (TLS visible in packet capture) — no plaintext SQL or data is observable

### AC-004: HTTPS-only — HTTP requests are permanently redirected
- **Given**: The platform is fully deployed
- **When**: `curl -I http://localhost/api/health` is executed
- **Then**: The response is HTTP 301 with `Location: https://localhost/api/health` — no API response body is served over HTTP

## Edge Cases
* **Mixed-content requests from SPA**: The React SPA must not make any `http://` API calls when deployed; the Content-Security-Policy header must include `upgrade-insecure-requests` to prevent accidental downgrade.
* **pgcrypto `pgp_sym_encrypt` with AES-128 fallback**: If the encryption key length is less than 32 bytes, the encryption call must be rejected at the application layer with a startup exception — it must not silently downgrade to AES-128.
