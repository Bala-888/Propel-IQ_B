# User Story - US_020

## Story ID
* ID Format: US_020

## Story Title
* ACID slot booking transaction with duplicate active booking conflict detection

## Description
* As a **patient**, I want my booking to be atomically committed so that I am guaranteed exactly one confirmed appointment even under concurrent access, and prevented from holding duplicate active bookings for the same time window.

## Acceptance Criteria

### AC-001: Successful booking creates a Confirmed booking record
- **Given**: An authenticated patient selects an Available slot and submits the booking
- **When**: `POST /bookings` is called with valid `slotId` and `patientId`
- **Then**: The response is HTTP 201 with `{"bookingId": "<uuid>", "status": "Confirmed", "slot": {...}}`, the `appointment_slots` row is updated to `status = "Booked"`, and both writes are committed in a single ACID transaction

### AC-002: Concurrent booking of the same slot returns 409 to the second requester
- **Given**: Two patients attempt to book the same slot simultaneously
- **When**: Both `POST /bookings` calls arrive within the same transaction window
- **Then**: Exactly one succeeds with HTTP 201, and the other receives HTTP 409 with `{"error": "This slot is no longer available.", "alternatives": [<3 available slot objects>]}` — the slot remains Booked with only one confirmed booking

### AC-003: `SELECT FOR UPDATE` prevents phantom booking
- **Given**: The booking API uses `SELECT FOR UPDATE` on the `appointment_slots` row
- **When**: An xUnit integration test executes 50 concurrent booking requests for the same slot
- **Then**: Exactly 1 booking is committed and 49 receive HTTP 409 — `SELECT COUNT(*) FROM bookings WHERE slot_id = <slotId>` returns 1

### AC-004: Duplicate active booking for the same time window is rejected
- **Given**: Patient ID 5 already has a Confirmed booking for slot on 2026-06-01 09:00–10:00
- **When**: `POST /bookings` is called for the same patient with a second slot overlapping the same time window
- **Then**: The response is HTTP 409 with `{"error": "You already have an active booking for this time window."}` and no second booking is created

### AC-005: Transaction rolls back if any sub-operation fails
- **Given**: The slot UPDATE succeeds but a subsequent booking INSERT fails (simulated by a constraint violation)
- **When**: The transaction boundary completes
- **Then**: The slot reverts to `status = "Available"` and no orphaned booking record exists — verified by querying both tables after the failure

## Edge Cases
* **Slot already Blocked by admin between load and booking**: If the slot status is `Blocked` (not `Booked`) at transaction time, the API must return HTTP 409 with `{"error": "This slot has been blocked by the clinic."}` — distinct from a concurrent booking conflict.
* **Booking transaction exceeds 10 seconds**: If the advisory lock or `SELECT FOR UPDATE` cannot be acquired within 10 seconds (long lock contention), the API must return HTTP 503 with `{"error": "Booking could not be processed. Please try again."}` rather than leaving the patient waiting indefinitely.
