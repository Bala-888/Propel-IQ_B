# User Story - US_010

## Story ID
* ID Format: US_010

## Story Title
* Enforce 15-minute session timeout and progressive login rate limiting

## Description
* As a **security officer**, I want authenticated sessions to automatically expire after 15 minutes of inactivity and failed login attempts to trigger progressive rate limiting, so that stolen tokens and brute-force attacks cannot be used to access protected patient data.

## Acceptance Criteria

### AC-001: Session timeout warning modal appears at 14 minutes
- **Given**: A user has been authenticated and inactive for 14 minutes
- **When**: The client-side inactivity timer fires
- **Then**: The session timeout warning modal (MOD-001) appears with a 60-second countdown and two options: "Stay signed in" and "Sign out now"

### AC-002: Session is invalidated at 15 minutes — re-authentication required
- **Given**: A user has been inactive for exactly 15 minutes and did not respond to the warning modal
- **When**: The inactivity timer expires
- **Then**: The access token is removed from client state, the user is redirected to `/login` with message "Your session has expired. Please sign in again.", and the JWT's `exp` claim has passed server-side

### AC-003: "Stay signed in" resets the inactivity timer
- **Given**: The session timeout warning modal is displayed
- **When**: The user clicks "Stay signed in"
- **Then**: The modal closes, a new access token is issued via the refresh token endpoint, and the 14-minute inactivity timer resets to zero

### AC-004: Progressive rate limiting activates after 5 failed login attempts
- **Given**: 5 consecutive failed `POST /auth/login` requests from IP `192.168.1.100` within a 15-minute window
- **When**: The 6th attempt is made from the same IP
- **Then**: The response is HTTP 429 with `{"error": "Too many failed attempts. Please try again in 15 minutes."}` and a `Retry-After: 900` header

### AC-005: Rate limit counter resets after the lockout window expires
- **Given**: IP `192.168.1.100` has been rate-limited for 15 minutes
- **When**: 15 minutes elapse and a new login attempt is made
- **Then**: The attempt is processed normally (not blocked) and the failed-attempt counter resets to 1

## Edge Cases
* **User activity detection**: "Activity" for the inactivity timer must include mouse movement, keyboard presses, and API calls — not just page navigation. A user actively typing in a form must not be timed out.
* **Multiple tabs**: If the user has the app open in two tabs and extends the session in one tab, the other tab's inactivity timer must also reset (achieved via a broadcast channel or shared storage event).
* **Rate limiting across load-balanced instances**: The failed-attempt counter must be stored in a shared data store (or via ASP.NET Core's distributed rate limiter) so that switching from instance A to instance B does not reset the counter for the same IP.
